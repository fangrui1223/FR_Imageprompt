**1. 重复收录保存时使用旧条目快照，可能产生没有图片的“成功收录”**

定位：`src/PromptVault.App/Services/CaptureCoordinator.cs:131`，以及保存成功后的 `pending.Dispose()`。

复现顺序：先正常收录图片 A；再次准备收录 A，使 `PendingCapture.ExistingItem` 保存第一次收录的条目；在第二次保存前，将原条目移入回收站并永久删除；再保存第二次收录。

结果：第二次保存正常返回，数据库重新创建了条目，但原图、小缩略图、中缩略图全部缺失，且第二次收录原本完整的暂存文件被清理。复现时使用本轮生成的 PNG，永久删除也仅作用于该合成图库。

原因：保存分支只要看到准备阶段缓存的 `ExistingItem` 就复用旧路径，跳过文件复制；仓储在自己的事务中重新判断为新图片并插入新记录，两层判断不一致。问题同样提示保存不能仅凭旧数据库记录判断文件已经持久化。

建议：把“目标资源可用”作为保存成功的前提；保存时核对当前条目和三份目标文件，缺失时使用仍保留的暂存文件完成持久化。对同一资源的保存、永久删除和提交后文件清理建立统一互斥/操作协议，避免只增加一次查询后仍留下竞争窗口。文件和数据库均完成确认后才清理暂存副本；失败继续保留可恢复捕获。

回归验收：复现上述顺序后，应当成功保存并可解码三份文件，或明确拒绝并保留暂存文件；不得再出现“保存成功且原图缺失”。同时覆盖原条目只进回收站、被永久删除、已有路径缺失、失败重试和重复并发收录。

**2. 撤销重复收录时无条件恢复旧快照，覆盖收录后的人工修改**

定位：`src/PromptVault.Core/LibraryRepository.Captures.cs:635`。`RestoreDuplicateSnapshotAsync` 只按条目 ID 更新，没有核对条目是否仍处于本次收录产生的状态，随后还会替换标签。

复现顺序：已有图片的提示词为 `original prompt`；重复收录将其改为 `duplicate prompt`；用户随后手工改为 `newer manual prompt`；在十秒撤销窗口内撤销本次收录。

结果：提示词从 `newer manual prompt` 恢复为 `original prompt`，后续手工备注也同样被覆盖。

建议的冲突规则：默认保留后续人工修改并提示撤销冲突。该规则已向用户提问，尚待选择时作为建议，不视为已批准的产品决策。实现上记录保存后的条目版本或准确内容指纹，在同一数据库事务内核对再恢复；发现不一致时保留当前条目并返回明确冲突结果。新收录的删除式撤销也应遵循同一保护规则，避免撤销入口误删已被继续整理的内容。

回归验收：无后续修改时仍精确恢复原提示词、备注、分类、标签和回收站状态；有后续修改或连续两次收录时，不静默覆盖新内容；十秒截止与状态机规则保持不变。

**3. 升级失败回滚会恢复已经被清理掉图片的过期回收站记录**

定位：`src/PromptVault.Core/LibraryRepository.cs:72`。

复现顺序：构造 v11 隔离迁移样本，包含一条超过 30 天的回收站记录及其三份文件；初始化迁移到 v12；在 `ValidationCompleted` 检查点注入 I/O 异常。

结果：回滚报告 `Recovered=true`，数据库记录已经恢复，但三份图片全部缺失。该复现严格限定为过期回收站资源，未观察到此路径删除正常活跃图片。

原因：`PurgeTrashAsync(30)` 在 `upgrade.CompleteAsync` 之前运行，它已提交数据库删除并永久删除图片文件；后续升级完成环节失败进入数据库回滚，恢复协议只备份数据库与设置，无法恢复已删除图片。

建议：让升级、最终验证和升级状态落盘完整结束后，再独立执行回收站维护；维护失败不得重新进入升级回滚。仅把两行互换还不够，应明确分开异常边界，避免清理过程中异常又触发旧库恢复。恢复报告增加引用文件一致性结果，准确报告“数据库已恢复”与“图片缺失”。

回归验收：在每个升级阶段注入故障，合成回收站资源仍可随数据库恢复；升级完成后的清理故障只产生维护失败，不把已经运行成功的数据库恢复成旧版本。保留 30 天清理规则和升级不覆盖原图的产品契约。

**4. 下载完成后仍持有独占写入流，立即读取自己的文件失败**

图片入口：`src/PromptVault.App/Services/CaptureCoordinator.cs:76`。`await using var output` 的生命周期覆盖了后续 `RegisterAndProcessAsync` 调用；Flush 不会关闭文件，解码阶段无法再次以读取方式打开。

实测：回环 HTTP 服务返回一张可以正常解码的合成 PNG，`CreateFromUriAsync` 产生 `CapturePreparationException`，最内层异常为 Windows 文件共享冲突 `0x80070020`，捕获会话变为 Failed。此问题不依赖远端图片损坏；本地文件收录控制路径正常。

同类位置：`src/PromptVault.Core/ModelPackInstaller.cs:27` 和 `:38`。`InstallFromUrlAsync` 下载 ZIP 后，在写入流尚未释放时执行 SHA-256 读取，产生同一共享冲突。使用内存 HTTP 响应与合成 ZIP 完成复现，外部请求为 0。当前主界面的模型入口调用本地 `VerifyAndInstallAsync`，因此不能据此宣称正常的本地 ZIP 导入失效；URL 安装接口可按较低优先级一并修复。

建议：下载阶段使用独立的 `await using (...) { ... }` 作用域，确保输出流释放后再转入解码/校验/解压；继续保持原有状态机接管、取消和失败清理语义，不采用放开独占锁来掩盖生命周期错误。

回归验收：直接测试 `CreateFromUriAsync` 与 `InstallFromUrlAsync` 的完整下载路径，覆盖正常下载、下载中取消、无效图片和 ZIP 校验失败。当前模型测试只调用本地文件校验安装，未覆盖出错的下载入口。

**5. 设置结构异常绕过既有恢复机制，导致启动失败**

定位：`src/PromptVault.App/Services/AppSettings.cs:55`。

最小输入：`{"LibraryRoot":"synthetic","GalleryLayouts":{"library":null}}`。

结果：JSON 语法正确且可反序列化，但执行 `preference.Normalize()` 时触发 `NullReferenceException`。当前捕获只处理 `JsonException` 与 `NotSupportedException`，所以不能走“保留损坏设置并恢复”路径。此问题的前提是设置中存在异常成员；正常设置文件未复现该问题。

建议：归一化设置前显式校验集合成员，对 null 的布局值恢复单项默认配置，保留已有 LibraryRoot 和其他有效设置；外部目录及其他嵌套成员一并做同类结构校验。不要用捕获全部异常并整份静默重置代替字段级恢复。

回归验收：空集合、null 集合、null 成员、缺失字段和旧版设置分别覆盖；合法部分保留，无法修复的原文件先备份，不能因一个布局成员而丢失全部配置。
